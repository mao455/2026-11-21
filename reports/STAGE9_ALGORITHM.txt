Stage9 跨文件算法与两条真实轨迹

本文路径均相对 FingerEyeLab；E=experiments/rax_dexbin_tinyobj，O=outputs/rax_dexbin_tinyobj/stage9_20261121。
冻结代码以 E/versions/visual_stage9_early_v9/controller.py 为准，源码同名函数多次覆盖，必须读最终绑定或保存的 _S*_ 别名，不能只看第一次 def。
配套参数表：E/STAGE9_CONTROL_AUDIT.txt；运行命令：E/STAGE9_EXECUTION.txt。
本文两条轨迹来自runtime v1；最终runtime v2的同一冻结控制器另以verified_*复验，接口/录像修正没有调整策略。本文数据由两条实际 rollout 的 agent_trace.jsonl/public_responses.jsonl/result.json 提取。O/trajectory_excerpt.json 保存每个关键事件完整18维曝光q、当前q、曝光qvel、六路文件路径、原始note、下一条命令及原始行号；不是手工推测的示意轨迹。

从入口到结束
run_stage9.py::main
 -> 读取 stage9_config.json，校验120/20/30/30；选择冻结controller，复制到episode/program
 -> stage9_episode.py::runtime.main（stage4_episode.runtime -> run_round14_episode.main）
    -> Peer启动 stage9_backend.py::main -> 对round14_backend.py断言替换 -> 保存stage9_backend_executed.py
    -> sandbox_command -> worker.py::main -> 冻结controller.py::main
       -> _S9_MAIN(_S9Context(ctx)) -> _s6_policy_main(_S6Context(...)) -> V7主FSM
       -> s5_init -> s5_plan -> s5_approach -> s5_refine -> s5_close
       -> s5_lift(.003,48) -> s5_decide('proof')
          retry -> s5_recover -> 下一次s5_plan
          continue_lift -> s5_lift(.0165,0) -> s5_decide('middle')
            continue_lift -> s5_lift(.03,360) -> s5_decide('final')
            reobserve -> s5_reobserve -> s5_decide('final',reobservations=1)
    -> controller返回 -> 后端finish -> evaluator.py::evaluate(records, initial_object_z)
    -> result.json/summary.json；完整记录模式Recorder.close等待编码线程结束。

命令与图像是两条时钟。动作统一从 s5_step 做原几何/关节/速率守卫，再经 _S6Context.step -> _S9Context.step -> worker.Context.step 序列化为op=step。host的validate_step验证合法请求，Peer.call送给后端请求循环；后端调用_set_q_state_and_target_batch下发目标，每次推进6个120Hz物理步。没有把关节实际值直接重置为目标。
后端每4步独立调用capture_sensor，capture_cameras渲染和读回六路160x120 RGB，同时保存该曝光的实际q/qvel。image_manifest.jsonl写帧号、物理时间、曝光状态和像素SHA；public_responses中actual_q是回包当时状态，image_state.actual_q是曝光状态。
ObservationGuard只放行RGB、当前/曝光本体状态和静态标定。私有对象姿态、接触、严格分数不进入策略。S9FrameInbox.select立即取最近有效曝光；迟到旧帧不回滚，重复帧不刷新时间，缺帧保留旧估计，仿真帧龄>.1秒停止。单元测试覆盖这些情况，正常物理轨迹并没有刻意注入真实驱动丢帧。

具体消费与中间状态
1. s5_init由主FSM调用，_S3_ESTIMATE读取step0的initial_overhead.npy和标定；Robot载入URDF，初始体素体积、中心/半长轴/方向写入s['info']/s['volume']，SelfAwareGeometry保存完整机器人碰撞模型。
2. s5_plan读取当前RGB估计包络和当前实际关节，_s3_candidates_on_axes -> optimize / close_ik求指垫点/法向IK，checker.check检查端点与整段路径。接受候选存s['c']，保存合法末命令s['last']。第2抓正交；第3抓由V7规则选±45度中当前包络投影较窄方向。
3. s5_approach遍历候选prefix，raise/orient/translate/descend由smooth_segment生成6步命令；下降90%处调用s5_refine。Stage3LiveVolume.carve -> frames -> _s9_volume_frames -> s9_exposure用曝光q做相机FK，避免用回包q错配像素；包络变化<.8mm时保留原轨迹，>=.8mm才重求IK并完整检查连接。此处并非每个tick重建地图。
4. s5_close最后绑定到Stage9包装，继承V7闭合/预载。30个闭合IK目标、初始至少.2s稳定等待，再由capture_preload_snapshot读取新帧，compare_preload比较轮廓/运动与本体响应；squeeze、features、闭合动作及响应写入note。闭合稳定判据用实际手指qvel<.06rad/s，早采样本身不能称为RGB收益。
5. s5_lift(.003,48)由主FSM调用。stage3_support_snapshot把六路分割特征与曝光q封装；stage3_support_pair用前后相机运动和轮廓变化区分carrying/grounded/unknown。Stage9只在曝光腕部实际上移>=2.2mm后提前调用原grounded/proof决策；只有retry或stop_limit才截断剩余微抬和等待。成功轨迹不会因为帧多就提前宣布抓稳。
6. stage3_support_decision还要求原稳定窗口：10份独立报告、跨度>=240物理步。缓存同帧特征不会增加独立证据；保留段虽然拆成6步回包，报告仍按24步产生。s5_decide输出公开证据层状态，明确private_success_certified=false。
7. s5_recover -> stage3_recover -> _Stage3Mover先张开再竖直退让；stage3_live_geometry从新的曝光RGB重建包络，检查实测和命令姿态的完整手部间隙。若仍重叠，按4mm档额外退让、稳定后重新观察；只有fresh_envelope_and_hand_clear才允许下一次规划。
8. 后端每个物理步保存严格几何和原生接触/速度，evaluator.evaluate在最终连续2秒窗口裁决。公开stop_supported不能替代strict success。录像完整模式在capture_sensor后把同次RGB交给Recorder.capture，外部视图与六路拼图入队；最终runtime v2复用既有third_view顶视图，不增加相机render product；Recorder.encode后台编码30fps，逐帧对应recording_frames.jsonl。最少日志模式保留全部六路策略RGB，禁用这条额外录像链。

时间与数组约定
control_tick=step/6，首次观测为tick0；物理秒=step/120；曝光frame_id=capture_step/4。下表“帧/曝光step/曝光秒”明确指出视觉读哪个时刻。q数组按episode.json/scene标定的18关节顺序：前三项平移米，其余转动弧度。完整数组不做截断，存trajectory_excerpt.json的capture_q/current_q；每行原始数据也可按public_responses.jsonl行号直查。
例如成功轨迹control tick1在step6/.05s收到frame1/step4/.033333s，视觉读取q[step4]，命令继续使用q[step6]，帧龄1/60秒；tick2在step12/.1s取得frame3/step12/.1s。frame2确实在step8采集，但20Hz消费者按最新帧规则跳过，不能把“未消费”误称为没有采集。

复核方法与边界
读取trajectory_excerpt.json可逐个事件跟踪：payload给出中间结果与决策原因，capture_q给视觉FK输入，current_q给控制器当前本体输入，next_dispatch.command.target_q给实际下一命令，trace_line/public_response_line直达未裁剪原始日志。phase_starts列出所有阶段及秒数；完整分阶段耗时仍以stage9_timing_summary.json为准。示例中的“当前q”是最近实际状态，并非预期轨迹目标，target_q必须从next_dispatch读取。
本文件描述的成功/失败由物理rollout给出，回放只测计算时延。真机结论限于120/20/30接口时序、曝光状态配对、输入隔离和记录输入上的控制计算；不含真实相机驱动、真实总线延迟或真实接触验证。

帧率与决策调度的归因：V8只提高采集频率，没有动作时间收益。V9第一抓20.5秒的grounded触发在Stage8原记录同一物理时间已经可观察；旧逻辑等到21.6秒才裁决。故3.25秒实测缩短证明提前消费/裁决的价值，不能声称这由30fps独有的新画面造成。未做保持V9决策逻辑的20fps采集独立消融。
